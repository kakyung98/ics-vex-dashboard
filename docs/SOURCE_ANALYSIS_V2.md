# 소스 분석 로직 v2 재설계

작성일: 2026-11-01. 상태: **설계 기준 및 단계적 구현**. C/C++용 Clang/LLVM IR
CFG·직접 호출 그래프와 빌드/범위/경로 설명은 기본 웹 경로에 구현했다.
[구현 범위](CLANG_SOURCE_REVIEW.md)를 참조한다. 아래 Joern 데이터 흐름·기호 실행·
배포 바이너리 연결 및 전체 증거 심사 설계는 여전히 미구현이다. 신규 Clang을
267건에서 검증했다고 주장하지 않으며, 기존 결과와 평가 정답은 덮어쓰지 않는다.

## 1. 해결할 문제와 현재 기준선

현재 수집물은 CVE별 소스 스냅샷 267건, 부품명 25개다. 메타데이터의
`(component, version, tag)` 조합은 136개지만 내용 해시로 검증한 중복 제거 수는
아니다. 동일 부품·릴리스가 여러 CVE에 반복된다.

기존 자체 CFG 전체 실행: 267건 시도, 249건 blocked, 18건 timeout, CVE 단위
도달성 확정 0건. 이는 검출 성능이나 안전 판정 정확도가 아니다.
`results/source_cfg_batch/summary.json`을 기준선으로 보존한다.

확인한 구조적 문제:

- 제품 소스와 라이브러리 소스를 같은 입력으로 취급했다.
- 빌드에 들어가지 않는 테스트·예제·타 언어 파일까지 전체 실패 사유로 삼았다.
- 함수명을 전역 키로 사용해 서로 다른 파일의 static 함수가 충돌했다.
- CVE 패치에서 변경한 함수를 취약 함수의 완전한 목록처럼 취급했다. 추가된
  방어 함수나 수정과 무관한 변경도 섞일 수 있다.
- 전처리와 실제 빌드 구성이 없는 상태에서 원문 C를 파싱했다.
- 라이브러리에 main이 없다는 이유로 막혔고, 외부 호출을 모두 불명으로 처리했다.
- 함수 미검출, 분석 불완전, 실제 부재를 충분히 구분하지 못했다.

## 2. 분석 단위

최종 VEX의 단위는 `제품 ID + 제품 릴리스 + 빌드 설정 + 부품 인스턴스 + CVE`다.
같은 CVE라도 다른 제품이나 설정에는 별도 결론을 낸다.

| 입력 모드 | 가능한 결과 | 금지할 결론 |
| --- | --- | --- |
| 제품 소스·빌드·통합 정보 보유 | 선택한 제품/빌드 범위의 VEX | 다른 설정·릴리스·제품까지 일반화 |
| 부품 소스만 보유 | 취약 위치, 패치 상태, 공개 API에서의 조건부 경로 | 제품에서 도달 불가라는 확정 |
| 일부 파일/함수만 보유 | 국소 코드 관찰과 후보 위치 | 제품 전체에서 취약 코드 부재 |

각 모드는 `analysis_scope`로 결과에 남긴다. 라이브러리 분석을 성공적으로 끝내도
제품 VEX는 통합 정보가 없으면 under_investigation일 수 있다. 분석 성공과 VEX
확정은 서로 다른 지표다.

## 3. 전체 흐름

```text
SBOM에서 식별한 CVE 후보
  → 제품/부품/소스/버전 연결 검증
  → CVE의 취약 위치·조건·수정 근거 검증
  → 선택한 빌드의 포함/제외 확인
  → 진입점과 호출 그래프 + 함수별 CFG
  → 공격 입력의 데이터 흐름과 취약 조건 분석
  → 증거·분석 범위 심사
  → VEX + TIX + 미확인 근거
```

단계는 `pass / fail / unknown / not_applicable`을 명시한다. 실행기는 별도로
`completed / partial / blocked / timeout / error`를 기록한다. unknown을 fail이나
false로 바꾸지 않는다. 앞 단계의 유효한 부재 증명은 뒤 단계 실행을 요구하지
않는다. 취약 코드가 없으면 CFG나 제어 가능성 분석을 하지 않아도 된다.

## 4. 단계별 입력과 증거

### S0. 제품·소스·CVE 연결

제품·부품 ID, 버전, 소스 커밋/트리 해시, 패키지 식별자와 출처를 연결한다.
NVD 범위의 하한 버전으로 수집한 소스는 실제 설치 버전의 소스로 간주하지 않는다.
배포 바이너리와의 연결은 별도 `deployment_binding`으로 표시한다. 배포 연결이
없으면 분석 대상 소스/릴리스까지만 주장한다.

### S1. 취약 위치와 조건 정의

입력은 공식 어드바이저리, 검증한 수정 커밋, 해당 버전의 코드다. 패치의 삭제·변경
위치, 취약한 연산, 입력/객체, 취약 조건을 구조화한다. 함수가 아닌 매크로·전역
초기화·생성 코드의 취약점도 표현한다.

심볼 ID는 `소스 revision + 번역 단위 + 경로 + qualified name + signature`다.
파일별 static 함수, 이름 변경, 인라인 구현, 대체 구현을 구별한다.

패치 변경 함수 전체, 문자열 일치, 설명에서 추출한 함수명은 **후보**다.
검증한 취약 위치 목록과 완전성 범위를 별도로 둔다. LLM은 후보와 조건 초안을
제안할 수 있지만 취약 위치 확정, 분석 완전성 선언, 최종 VEX 발급은 하지 않는다.

### S2. 빌드 구성과 코드 존재

C/C++는 compilation database의 working directory, arguments, target/sysroot,
include 경로, 매크로, 생성 헤더를 복원한다. 동일 파일의 서로 다른 컴파일 명령은
별도 설정으로 취급한다. Clang 기반 전처리·AST/CFG 추출을 사용한다.
Clang 호환이 안 되는 타깃은 적절한 프런트엔드가 준비될 때까지 unknown이다.

번역 단위가 목록에 없다는 사실만으로 제외했다고 결론 내리지 않는다. 헤더·매크로,
정적/동적 라이브러리, 생성 코드, 링크 결과와 런타임 로딩까지 포함 범위를 확인한다.
링크 map, 객체/라이브러리·실행파일의 심볼 및 해시를 보조 증거로 사용한다.
심볼이 없다는 것만으로도 인라인·strip·LTO 때문에 부재를 확정하지 않는다.

미검출은 absent가 아니다. `present / absent_proven / unknown`을 분리하고,
absent_proven에는 포함/제외 규칙과 확인한 범위를 첨부한다.

업로드 서버는 자료만 수집한다. 빌드 재현이 필요하면 별도 격리 실행기가 제한된
작업공간·자원으로 승인된 툴체인을 실행한다. 업로드한 shell 명령을 호스트에서
그대로 실행하지 않는다. 재현 빌드와 배포 바이너리 동일성도 각각 기록한다.

### S3. 도달성: 호출 그래프와 CFG 결합

제품 진입점은 main만이 아니다. 초기화 함수, 인터럽트/이벤트 핸들러, 등록된 콜백,
스레드 시작 함수, RPC/프로토콜 핸들러, 플러그인 진입점도 수집한다.

라이브러리 모드는 내보낸 공개 API와 초기화 경로를 보수적인 루트로 사용한다.
테스트에서 호출하지 않는다는 이유로 라이브러리 취약점을 제외하지 않는다.
실제 제품 호출 지점이 확보되면 제품 모드의 그래프로 연결한다.

함수 내부는 CFG, 함수 간은 호출 그래프를 사용한다. Joern CPG로 경로를 조회하고
Clang 빌드 정보와 소스 위치로 대조한다. 함수 포인터·가상 호출·콜백·별칭을
해결하거나 가능한 대상으로 보수적으로 확장한다. 미해결 호출은 unknown edge로
남겨 취약 위치에 영향을 줄 수 있는지 확인한다.

단순 그래프 경로는 실행 가능성이 있는 경로다. 경로가 있으면 도달성 근거가 되지만
모든 경로가 실제 실행 가능하다는 뜻은 아니다. 조건 분석으로 불가능한 경로를
제외할 때는 제약과 근거를 보존한다. 깊이 제한·timeout·solver unknown은 도달
불가가 아니다.

도달 불가 결론은 정한 진입점·빌드·취약 위치 범위에서 가능한 경로를 보수적으로
포괄했고, 관련 미해결 간선이 없을 때만 허용한다. Joern이 그래프를 생성했다는
사실 자체는 완전성 증명이 아니다.

### S4. 제어 가능성과 취약 조건

도달 가능하면 공격 입력 source와 취약 연산 sink를 정의한다. 네트워크·파일·IPC·
설정 입력은 실제 공격 모델에 따라 구분한다. Joern 데이터 흐름으로 인자·필드·
별칭·호출 간 전파를 추적하고, 검증/변환/길이 제한 같은 sanitizer를 검증한다.
암호·상태 기계·경쟁 조건 등의 취약점에는 단순 source-sink 모델이 부족함을 남긴다.

필요한 후보 경로에 대해 기호 실행/제약 해결을 적용한다. solver는 다음을 나눈다.

- SAT: 모델의 조건을 만족하는 입력 후보. 실제 제품 악용의 자동 확정은 아니다.
- UNSAT: 해당 모델·경로 범위의 불가능성. 전체 경로를 포괄하지 않으면 전체 안전
  판정으로 확대하지 않는다.
- UNKNOWN/timeout: 판단 유보.

실제 취약 조건을 확인한 재현 증거 또는 검토된 적용성 근거가 있을 때 affected를
확정한다. 컴포넌트 단위 재현은 그 컴포넌트 범위의 근거이며, 제품 통합을 자동
증명하지 않는다. 테스트 실패나 크래시만으로 CVE와의 인과관계를 확정하지 않는다.
퍼징에서 재현하지 못했다는 사실은 not_affected 증거가 아니다.

## 5. 최종 판정 규칙

공통 전제: 주장하는 제품/부품·버전·빌드·범위를 증거에 연결했고 관련 분석의
불완전성이 결론을 뒤집을 수 없어야 한다. 증거가 충돌하면 자동 확정을 중단한다.

| 검증된 사실 | VEX 상태 | justification/설명 |
| --- | --- | --- |
| 대상 제품/빌드에 취약 부품이 없음 | not_affected | component_not_present |
| 부품은 있으나 취약 코드가 해당 빌드에 없음 | not_affected | vulnerable_code_not_present |
| 취약 코드가 있지만 정한 모든 진입점에서 도달 불가 | not_affected | vulnerable_code_not_in_execute_path |
| 도달 가능하지만 공격자가 취약 조건에 필요한 입력을 제어할 수 없음을 증명 | not_affected | vulnerable_code_cannot_be_controlled_by_adversary |
| 모든 관련 경로의 유효한 방어 코드가 취약 조건을 차단함을 증명 | not_affected | inline_mitigations_already_exist |
| 해당 범위에서 취약 조건 성립과 적용성을 확인 | affected | 검증 경로·조건·근거 첨부 |
| 수정 적용·완전성·해당 릴리스/빌드 연결까지 확인 | fixed | 고정 버전/수정 증거. 패치 문자열 일치만으로 불가 |
| 위치·빌드·진입점·호출·조건 분석 중 필요한 근거가 미확정 | under_investigation | 막힌 단계·필요 입력·후속 작업 명시 |

내부 상태는 출력 형식과 분리한다. OpenVEX/CSAF별 허용 필드와 상태·justification
대응을 검증하는 어댑터를 거쳐 내보낸다. 조건부 컴포넌트 결과를 제품 VEX로
무조건 승격하지 않는다. 도달 가능성·우선순위 점수는 affected의 대체값이 아니다.

## 6. 분석 범위와 부분 실패 처리

전처리가 필요한 파일을 즉시 실패로 처리하지 않고 준비 단계로 보낸다. 관련 없는
테스트 파일의 언어가 다르다고 제품 분석 전체를 실패시키지 않는다. 실제 빌드
대상과 취약 위치 의존 범위를 먼저 정한다. 제외 근거 없는 파일은 임의로 버리지
않는다. 외부 함수는 검증한 버전별 호출/데이터 흐름 요약을 사용하며, 관련 모델이
없거나 콜백 가능성이 해결되지 않으면 그 경로를 unknown으로 남긴다.

분석 범위 기록에는 타깃·진입점·관련 번역 단위, 파싱 누락, 미해결 간접 호출,
외부 모델, 경로/시간 한도와 가정을 포함한다. 단일 `complete=true` 사용자 체크로
이를 대체하지 않는다. 퍼센트 하나가 임계값을 넘었다고 안전으로 판정하지 않는다.

## 7. 도구와 모듈 경계

| 역할 | 채택할 구성 | 주의점 |
| --- | --- | --- |
| 빌드 문맥·전처리·AST/CFG | Clang/LLVM + compile_commands | 버전/타깃·빌드 재현 검증 필요 |
| 호출·제어·데이터 흐름 탐색 | Joern CPG | 결과가 자동으로 sound/complete인 것은 아님 |
| 경로 조건 | 기호 실행/SMT 어댑터 | C 정수·메모리 의미와 경로 범위 일치 필요 |
| 최종 VEX | 결정적 증거 심사기 | LLM 점수와 도구 성공 코드만으로 결정 금지 |
| 기존 pycparser 자체 CFG | 제한된 입력의 진단·회귀 비교 | 주 분석 엔진으로 사용하지 않음 |
| 비 C/C++ 언어 | 언어별 백엔드 | Java/Python을 C 파서로 처리하지 않음 |

새 모듈은 `source_case`, `vulnerability_spec`, `build_context`, `graph_backend`,
`reachability`, `controllability`, `evidence_policy`, `source_report`로 나눈다.
API/UI/일괄 실행기는 동일한 오케스트레이터와 정책을 사용한다.
현재 `source_evidence.py`와 `batch_source_cfg.py`의 서로 다른 규칙은 대체한다.

실행 순서:

1. source case와 취약 위치 스키마, 증거 심사기, 단계별 상태/이유 계약 구현.
2. Linux 격리 실행 환경과 재현 가능한 C/C++ 빌드 수집부터 검증. 현재 Windows
   환경에서 Linux 프로젝트를 호스트 MSVC로 대체 빌드하지 않는다.
3. zlib, libexpat, OpenSSL 등 대표 부품을 실제 빌드 입력으로 분석. 공개 API 루트와
   제품 통합 루트의 결과가 다름을 별도 테스트. 예제 앱은 실제 제품으로 표기하지 않음.
4. Clang/Joern 도달성 통합과 범위 보고, 그 다음 입력 흐름/취약 조건 분석 구현.
5. 취약/수정 버전 대조와 사람이 검토한 근거로 검증 후 267건 전체 재실행.
6. 동일 실행을 로컬 웹의 작업 큐·단계 표시·결과/증거 다운로드와 연결.

## 8. 평가와 완료 기준

267건 각각에 명시적인 단계 결과가 있어야 한다. 실험 빌드는 제품의 실제 설치
빌드와 구분한다. 내용·설정·툴 버전의 해시가 같을 때만 그래프를 재사용하고,
같은 부품의 다른 CVE는 다른 취약 위치/조건으로 따로 질의한다.

필수 지표:

- 수집 수 267, 소스/버전 연결 검증 수, 취약 위치 검증 수.
- 실제 빌드 복원 수, 그래프 생성 수, 관련 범위 분석 가능 수.
- 도달성 확정 수, 제어/조건 확정 수, 최종 상태별 수, 유보 원인별 수.
- 검토된 정답이 있는 범위의 오판정 수, 특히 잘못된 not_affected 수.
- timeout/error, 언어·부품·제품/라이브러리별 분모와 실행 비용.

파싱 성공·완전한 도달성 분석·VEX 확정을 별도 집계한다. 잘못된 not_affected는
실제 영향이 있는 사례를 제외한 오류다. 검토 표본에서 오류 0건이어도 전체 정합성
증명이라고 보고하지 않는다. 개발에 사용한 회귀 fixture와 독립 평가 사례를 분리하고
같은 부품·릴리스·패치가 양쪽에 섞이지 않도록 한다.

대표 회귀 사례: 취약 위치 부재, 일부 위치만 부재, 빌드 제외, 호출 도달 불가,
콜백/인터럽트로 도달 가능, static 동명 함수, 동적 로딩, 매크로/인라인 취약점,
검증 로직 우회, SMT unknown, 다른 버전의 패치, 관련 없는 파일의 파싱 실패,
부분 소스, 제품 정보 없는 라이브러리, 변경되지 않은 배포 바이너리.

## 9. 현재 구현과의 관계
