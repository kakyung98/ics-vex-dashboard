# 방법론 v3 — S/HBOM → CVE 식별의 6W 문제 정의와 CVSS·운영맥락 기반 VEX 판단

> **이 문서가 바꾸는 것**
> 1. SBOM/HBOM으로 CVE를 식별할 때 생기는 문제를 **6W 축**으로 분해하고, 각 문제를
>    **해결됨 / 부분해결 / 원리적 불가**로 판정한다.
> 2. VEX 판단의 **주 경로를 소스코드 분석에서 CVSS 전체 벡터 + ICS 자산 운영맥락으로
>    교체**한다. 소스 기반 게이트는 소스가 존재하는 소수 분기로 격하한다.
>
> 근거는 모두 본 저장소 코퍼스에서 측정한 값이며, 문서에 적어둔 숫자가 아니라
> `python src/sbom_cve_problems.py` 가 매번 재계산한다.

## 0. 왜 바꾸는가 — 측정값 하나로 정리되는 문제

| 측정 항목 | 값 | 출처 |
|---|---|---|
| 소스 입수 가능 여부가 선언된 부품 중 **소스 폐쇄(E)** 비율 | **90.87%** | `src/sbom_cve_problems.survey()` |
| 식별된 CVE 중 **CVSS 벡터 보유** 비율 | **95.06%** | 동일 |
| 자산 중 **ICS 운영맥락 속성 보유** 비율 | **0.00%** | 동일 |
| 부품 중 **version 필드가 NOASSERTION** | **100.00%** | 동일 |
| 부품 중 **CPE 보유** | **1.58%** | 동일 |

세 줄로 요약된다.

- 소스는 **없다**(90.87% 폐쇄). 그래서 `vulnerable_code_not_present` 와 실제 실행경로 분석을
  주 방법으로 쓸 수 없다. 기존 소스 캠페인이 다룬 267건은 전체 식별 CVE 11,550건의 **2.3%**다.
- CVSS는 **거의 다 있다**(95.06%). 그래서 "이 취약점이 환경에 무엇을 요구하는가"는
  전수에 대해 말할 수 있다.
- 운영맥락은 **SBOM에 없다**(0.00%). 그래서 추론 대상이 아니라 **선언된 입력**이어야 한다.

> 기존 방법론은 가장 강한 근거(소스)를 주 경로에 놓고 2.3%만 처리했다. v3은 전수에
> 적용되는 근거(CVSS 요구조건 + 자산 사실)를 주 경로로 놓고, 소스는 있을 때만 쓰는
> 보강 경로로 돌린다.

## 1. 6W 문제 정의

CVE 식별은 "이름 맞추기" 하나가 아니라 **서로 다른 6개의 동일성 질문**이다. 실패 원인도,
해결 전망도 축마다 다르다.

| 축 | 질문 | 무엇이 걸려 있는가 |
|---|---|---|
| **WHO** | 누구의 제품인가 | 공급사 동일성 — 공유코드 CVE의 벤더 공동등재, 벤더 표기 비정규화, OEM 리라벨 |
| **WHAT** | 무슨 제품인가 | 부품 동일성 — 식별자 부재, 표시명이 산문, SBOM 완전성 |
| **WHEN** | 어느 빌드이며 언제 기준인가 | 버전·영향범위, 코퍼스 신선도 |
| **WHERE** | 어디에 놓여 있는가 | 내장 계층(제품 아래), 자산 배치·운영맥락 |
| **WHY** | 왜 취약한가 | 취약 코드와 발동 조건 |
| **HOW** | 그걸 어떻게 아는가 | 매칭 자체의 근거 추적성, 주장의 책임 소재 |

### 1.1 전체 문제 목록과 판정

`src/sbom_cve_problems.PROBLEMS` 가 기계판독 원본이고, 아래는 그 요약이다.
판정 집계: **해결 4 / 부분해결 5 / 원리적 불가 5.**

| ID | 축 | 문제 | 판정 | 측정값 |
|---|---|---|---|---|
| W1 | WHO | 공유코드 CVE가 이를 탑재한 모든 벤더를 등재 | 해결 | CVE 중 **15.45%** 가 2개 이상 벤더 등재 |
| W2 | WHO | 벤더 표기가 정규형이 아님 (OEM 리라벨 포함) | 부분해결 | — |
| W3 | WHAT | ICS 부품은 기계 식별자가 거의 없음 | 부분해결 | CPE 보유 **1.58%** |
| W4 | WHAT | **SBOM은 자신의 완전성을 증명할 수 없음** | **불가** | 측정 불가(원리상) |
| W5 | WHEN | version 필드가 실무상 비어 있음 | 부분해결 | NOASSERTION **100%** |
| W6 | WHEN | **설치된 버전은 문서에 없음** | **불가** | 표시명에서 범위 복원 **52.88%** |
| W7 | WHEN | SBOM은 스냅샷, CVE는 계속 늘어남 | 해결 | — |
| W8 | WHERE | 취약 코드는 제품보다 한 계층 아래 | 해결 | 내장 3rd-party 계층 **1.42%** |
| W9 | WHERE | **운영맥락이 SBOM에 없음** | **불가** | 보유 자산 **0.00%** |
| W10 | WHY | **ICS 소프트웨어의 소스는 입수 불가** | **불가** | 소스 폐쇄 **90.87%** |
| W11 | WHY | CVSS 없는 CVE는 요구조건을 진술하지 않음 | 부분해결 | 벡터 없음 **4.94%** |
| W12 | WHY | **공격자 측 조건(AC:H)은 자산 사실이 아님** | **불가** | 원리상 |
| W13 | HOW | 근거 없는 매칭은 검토 불가 | 해결 | 경로별 정밀도 분리 보고 |
| W14 | HOW | 맥락 반박은 사람의 주장이다 | 부분해결 | 미서명 시 UNATTESTED 표기 |

### 1.2 "해결 불가"가 뜻하는 것 — 추측 금지, 입력화 또는 거부

불가 5건은 알고리즘을 더 잘 만들어 메울 수 있는 종류가 아니다. 문서에 없는 사실을
파싱으로 복원할 수는 없다. v3은 이것들을 **셋 중 하나로** 처리한다.

| 문제 | 처리 | 구현 지점 |
|---|---|---|
| W4 SBOM 완전성 | **주장 범위를 축소한다.** 재현율은 "SBOM이 선언한 부품 기준"으로만 진술하고, 절대 "장비에 설치된 소프트웨어 기준"으로 말하지 않는다 | 문서 규약 |
| W6 설치 버전 | **입력으로 선언한다.** 자산 소유자가 제공하거나 장비를 조회한다. 그때까지 해당 부품의 CVE는 후보로 남고 `version-undecidable` 로 표기 | `cpe_match_l0l3._in_declared_range` 가 `None`(판단불가)을 `False`로 읽지 않음 |
| W9 운영맥락 | **입력으로 선언한다.** `src/ics_context.CONTEXT_FIELDS` 로 수집, SBOM에 있으면 선채움. 벤더명·장비명·권고문에서 **추론하지 않는다** | `ics_context.from_sbom()` |
| W10 소스 부재 | **해당 판정을 영구 포기한다.** 맥락 경로는 `vulnerable_code_not_present` 를 **낼 수 없게** 설계됨(매핑 테이블에 항목이 없음) | `vex_context_judge.JUSTIFICATION` |
| W12 AC:H | **반박 불가로 고정한다.** 무조건 `unknown` 반환 | `ics_context._eval_ac_h` |

## 2. 수정된 방법론 — 2개 arm, 1개 공통 식별부

```
S/HBOM 입력
   │
   ├─ Stage 1  부품 해소        (WHO · WHAT · WHERE-계층)
   │    식별자 우선 캐스케이드: 모델코드 → purl → cpe → 정확명 → 정규화명 → 제한적 유사도
   │    계층 분리: ics-product / product-variant / embedded-component
   │    해소 실패 = abstain (유사도로 메우지 않음)
   │
   ├─ Stage 2  CVE 식별          (WHEN · WHO-신뢰도 · HOW-근거)
   │    NVD CPE 인덱스 조회 → 후보 CVE
   │    버전 3값 판정 (True/False/None), None은 절대 False로 읽지 않음
   │    벤더 근거 등급 anchored / canonical / co-listed (하드필터 아님)
   │    산출물: 부품–CVE 매핑 + 경로별 근거 + 6W 진단 (diagnose())
   │
   └─ Stage 3  VEX 판정 — 두 갈래
        │
        ├─ [주 경로] 맥락 arm   ← 전체 CVE의 95.06%에 적용 가능
        │    src/vex_context_judge.py
        │    CVSS 전체 벡터 → 환경 요구조건 추출
        │    자산 운영맥락 → 요구조건별 4값 평가
        │    구조적 불가 → not_affected (CISA justification)
        │    그 외 → affected (+ 완화조치 remediation, + 환경점수 우선순위)
        │
        └─ [보강 경로] 소스 arm  ← 소스 입수 가능한 2.3%에만
             기존 patch gate + Q2 코드 존재 + Q3 도달 + Q4 제어
             여기서만 vulnerable_code_not_present 를 주장할 수 있다
```

**arm 선택 규칙은 능력이 아니라 사실로 정한다.** 부품의
`component:source-availability` 가 `A`/`C`(입수 가능)면 소스 arm, `E`면 맥락 arm이다.
두 arm이 같은 CVE에 모두 적용되면 **소스 arm이 우선한다** — 코드를 본 판정이 자산
사실에 대한 주장보다 강하기 때문이다.

## 3. VEX 판정 — CVSS Exploitability 메트릭 × ICS 운영맥락

### 3.0 먼저 — VEX가 답하는 질문과 답하지 않는 질문

**VEX는 "이 제품에서 이 취약점을 공격자가 악용할 수 있는가" 하나만 답한다.** 위험도 판단이 아니고 심각도 필드가 아예 없다. 따라서 자산이 자기에 대해 아는 것의 대부분은 **상태와 무관하다.**

CVSS 규격이 이 선을 이미 그어두었고, 파이프라인은 그 경계를 그대로 따른다. Base 메트릭군은 두 하위군으로 나뉘는다:

- **Exploitability metrics** (`AV / AC / PR / UI`) — 터뜨릴 수 있는가
- **Impact metrics** (`C / I / A`) — 터지면 무엇을 잃는가

**VEX 판정은 앞의 군만 읽고 나머지는 읽지 않는다.** `cvss.preconditions()` 가 반환하는 것도 AV/PR/UI/AC 뿐이고, C/I/A 는 `impact_profile()` 로 따로 빠져 점수에만 들어간다.

| | 메트릭군 | 쓰임새 |
|---|---|---|
| **VEX 상태** | Exploitability (`AV/AC/PR/UI`) + CTI 서비스 요구조건 | `not_affected` 를 설정할 수 있는 유일한 입력 |
| 우선순위 점수 (**VEX 아님**) | Impact (`C/I/A`) + `CR/IR/AR`, 망 위치에서 온 `MAV` | `affected` 더미의 순서매기용. 상태에 손대지 못한다 |

실행으로 확인 가능하다. exploitability 반쪽을 고정한 채 impact 반쪽을 `C:H/I:N/A:N` → `C:H/I:H/A:H` 로 바꿔도 상태는 전부 `affected` 이고 점수만 0.0 → 8.8 로 움직인다. 망 위치를 `remote-accessible` → `isolated-cell` 로 바꿔도 마찬가지로 전부 `affected`, 9.8 → 8.4. 상태를 뒤집는 것은 exploitability 반쪽 사실뿐이다 — NIC 미장착, 계정 체계 부재, 대화형 운영자 부재.

망 위치는 논란의 여지가 있다. 분할망에 있다는 것은 실제로 도달성 사실이므로 악용 가능성과 무관하지 않다. 그럼에도 상태를 못 내리게 막은 이유는 "무관해서"가 아니라 **되돌릴 수 있어서**다 — 방화벽 규칙 한 줄로 뒤집히는 판정은 발행된 문서에 들어가면 안 된다(§3.2).

그럼 우선순위 점수는 왜 내는가: VEX 는 "악용 가능"에서 멈추는데, L1 PLC 한 대에 `affected` 가 **5,129건** 남는다. 자산 소유자는 여전히 어디부터 손대야 하는지 정해야 하고, 그 순서에는 impact 반쪽이 필요하다. 단, **VEX 산출물이 아니라 옆에 붙는 별도 산출물**이며 `score` 필드로 분리돼 나간다.

### 3.1 핵심 아이디어 — 벡터는 점수이기 전에 요구조건 명세다

CVSS 벡터는 점수이기 전에 **요구조건 명세**다. `AV:N/AC:L/PR:H/UI:R` 은
"네트워크 경로가 있어야 하고, 관리자 계정을 이미 가지고 있어야 하며, 사람이 뭔가를
눌러줘야 한다"는 뜻이다. 자산은 그 요구조건을 공급할 수 있거나 없다.

exploitability 반쪽 안에서, 기존 `asset_av_judge.py` 는 **AV 하나만** 읽고 나머지를 버렸다.
v3은 네 개를 모두 요구조건으로 읽는다.

| 메트릭 | 값 | 환경이 공급해야 하는 것 | 자산이 반박할 수 있는가 |
|---|---|---|---|
| AV | N | 자기 브로드캐스트 도메인 밖에서 오는 경로 | **가능** — NIC 미장착, 단방향 하드웨어 다이오드가 유일 경로 |
| AV | A | 인접 세그먼트/무선/로컬 버스 경로 | **가능** — 유선·무선 모두 미장착 |
| AV | L | 자산에서 로컬 실행 능력 | **가능** — 콘솔·셸·사용자 로직 적재 모두 없음 |
| AV | P | 물리 접촉 | **가능** — 포트 포팅/제거(구조적)인 경우만 |
| PR | L/H | 해당 등급 계정 보유 | **가능** — 해당 인터페이스에 계정 체계 자체가 없음 |
| UI | R | 공격자 콘텐츠에 반응하는 사람 | **가능** — 헤드리스 제어기에는 사람이 없음 |
| AC | H | 공격자 통제 밖의 특수 조건 | **불가** (W12) |
| S | U/C | — (요구조건 아님, 영향 범위) | 해당 없음 |
| C/I/A | — | — (요구조건 아님, 영향 차원) | 해당 없음 → CR/IR/AR 가중에 사용 |

`PR:N`, `UI:N`, `AC:L` 은 요구조건의 **부재**를 진술하므로 검증할 것이 없다. 즉
`AV:N/AC:L/PR:N/UI:N` CVE의 요구조건은 단 하나이고, 맥락이 그것을 반박하는 길은
네트워크 자체를 없애는 것뿐이다 — 이 비대칭이 바로 "무인증 원격 RCE는 맥락으로
빠져나갈 수 없다"는 올바른 결론을 만든다.

### 3.2 이 설계의 중심 규칙 — 구조적 불가 ≠ 정책적 완화

```
STRUCTURAL   자산이 "무엇인가" 때문에 요구조건을 공급할 수 없다.
             무선 모듈 미장착, 유지보수 포트 포팅, 헤드리스라 사람이 없음.
             바꾸려면 하드웨어/펌웨어를 바꿔야 한다.
             → 건전한 반박. not_affected 를 설정할 수 있다.

CONTROL      자산이 "어떻게 설정·운영되는가" 때문에 지금은 공급되지 않는다.
             방화벽 규칙, 망분리, 캐비닛 잠금, 작업승인 절차.
             변경창 한 번, 설정 오류 하나, 노트북 든 엔지니어 한 명으로 되돌아온다.
             → 절대 not_affected 를 설정하지 않는다.
               affected 상태를 유지하고 CSAF remediation(category=mitigation)으로
               내보내며, 환경점수(우선순위)만 낮춘다.
```

기존 `asset_av_judge.py` 는 이 둘을 섞었다. 호스트 방화벽과 봉인된 포트가 똑같이
"공격벡터 차단"으로 처리되고, `likely_mitigated` 가 판정과 같은 필드에 앉아 있었다.
v3에서 둘은 **다른 타입이고 다른 결과를 낳는다.**

측정으로 확인된 효과: `control-network` 에 분리된 자산의 무인증 원격 RCE는
**`affected` 로 남는다**(완화 인정, 환경점수 9.8 → 7.7). 기존 로직은 같은 사례를
`not_affected` 로 지웠다.

### 3.3 절대 하지 않는 것

1. **`inline_mitigations_already_exist` 를 쓰지 않는다.** CISA 정의상 이 justification은
   **공급자가 제품에 내장한** 완화를 뜻한다. 운영자의 방화벽은 그게 아니다. 라벨을
   빌려 쓰면 기계판독 문서에 거짓 주장이 실린다. 운영자 통제는 `affected` + remediation이다.
2. **`vulnerable_code_not_present` 를 쓰지 않는다.** 폐쇄 펌웨어 내부는 어떤 배치 맥락으로도
   볼 수 없다. `JUSTIFICATION` 테이블에 항목 자체가 없어서 코드적으로 불가능하다.
3. **대화형 운영자의 부재를 `MUI:N` 으로 표현하지 않는다.** `MUI:N` 은 "사용자 상호작용이
   필요 없다"는 뜻으로 **점수를 올린다**. 사람이 없다는 사실은 요구조건을 충족할 수
   없다는 **반박**이다. 메트릭 값과 불가능성은 호환되지 않는다.
4. **반박된 진술에 환경점수를 매기지 않는다.** `not_affected` 면 환경점수는 0이다.
   계정 체계가 없다는 사실은 `PR:H` 를 반박하면서 동시에 `MPR:N` 으로 점수를
   올리므로, 둘을 한 레코드에 같이 쓰면 "적용되지 않으면서 발표된 것보다 더 심각하다"는
   자기모순이 된다.

### 3.4 justification 매핑

| 반박의 종류 | CISA justification |
|---|---|
| 채널 부재 (AV) | `vulnerable_code_cannot_be_controlled_by_adversary` |
| 권한 체계 부재 (PR / v2 Au) | `vulnerable_code_cannot_be_controlled_by_adversary` |
| 상호작용 주체 부재 (UI:R) | `vulnerable_code_cannot_be_controlled_by_adversary` |
| 해당 서비스 미구현 (CTI 유래) | `vulnerable_code_not_in_execute_path` |
| 부품 부재 / 버전 범위 밖 (Stage 2) | `component_not_present` |

서비스 반박이 여러 반박과 동시에 성립하면 **서비스 반박을 선택한다** — "그 코드 경로에
진입하지 않는다"가 "공격자에게 채널이 없다"보다 좁고 강한 주장이다.

### 3.5 반박의 사정범위 — `scope: as-scored`

NVD는 **가장 심각한 현실적 경로**를 점수화하며, 모든 경로를 점수화하지 않는다.
따라서 "이 CVE가 점수화된 네트워크 채널은 이 자산에 없다"는 문장은
"이 CVE는 이 자산에서 결코 악용될 수 없다"와 **같은 문장이 아니다.**

모든 반박은 `scope: as-scored` 를 달고 나가며, 자산에 다른 채널이 열려 있으면
잔여 위험이 명시된다:

> Residual risk: the asset still presents physical access. A CVE scored on one of
> those channels would not be refuted by this reasoning.

이 문장을 문서에 넣는 것이, 보기 좋은 VEX와 방어 가능한 VEX를 가른다.

### 3.6 우선순위 — CVSS 표준 환경점수 (상태가 아니다)

`affected` 로 남은 진술은 양이 많으므로 순서가 필요하다. 그 순서는 **CVSS v3.1
환경 메트릭군을 규격 그대로 계산**해서 매긴다. 자체 고안한 0–10 휴리스틱이 아니라
표준을 인스턴스화한 것이며, 이것이 인증 맥락에서 방어 가능한 유일한 형태다.

| 메트릭군 | 무엇으로 정하는가 |
|---|---|
| Modified Attack Vector (MAV) | 망 위치. `control-network` → `MAV:A`, `isolated-cell` → `MAV:L`, NIC 미장착 → `MAV:P`. CVSS가 MAV를 만든 목적 그대로("방화벽 뒤에 있으므로 원격 공격이 인접/로컬 공격이 된다") |
| Modified Privileges (MPR) | 해당 인터페이스가 인증을 **강제하지 않으면** `MPR:N` — 점수를 **올린다**. "PR:L이니 괜찮다"고 읽는 운영자가 틀렸음을 보여주기 위해 반드시 보고한다 |
| Modified Impact (MC/MI/MA) | 민감데이터 없음 → `MC:N`. 안전기능 수행 → `MA` 는 기준값 H 유지 |
| CR / IR / AR | 자산의 임무가 기밀성·무결성·가용성 각각을 얼마나 요구하는가. **OT 기본값은 IT 기본값이 아니다**: 보호계전기에서 가용성 상실은 트립이고 기밀성 상실은 불편이다 |

**CR/IR/AR 도출 규칙** (`ics_context.impact_requirements`)

1. **장비 유형에서 출발한다.** 제어기(plc/rtu/ied/sis)는 위조 명령(IR)과 정지(AR)가 모두 공정 사건이고 설정값 자체는 거의 비밀이 아니므로 `L/H/H`. 히스토리안은 기록이 가치이므로 정반대인 `H/M/L`. HMI·엔지니어링 워크스테이션은 제어 로직을 **쓰는** 장비라 그 무결성이 한 단계 건너뛴 제어기 무결성 문제가 된다.
2. **명시된 사실이 유형 고정관념을 이긴다.** `availability_tolerance`→AR, `data_sensitivity`→CR 은 직접 덮어쓴다.
3. **안전 자산은 AR뿐 아니라 IR도 올린다.** 직관적으로는 "멈추면 보호가 사라진다"라 AR만 올리기 쉬우나, **위조된 공정값으로 계속 도는 SIF가 더 위험하다** — 변조된 트립 로직은 보호를 소리 없이 무력화하고, 멈춘 로직솔버는 최소한 보인다.
4. **세 개를 모두 H로 올리지 않는다.** CVSS 가중치는 상대적이라 전부 올리면 기본 순서가 더 큰 배수로 복원될 뿐, 메트릭이 존재하는 이유인 변별력이 사라진다. 세 개가 모두 H가 되면 임무가 가장 덜 의존하는 축을 M으로 내린다 — 공정 자산은 CR, 정보 자산은 AR.
5. **임무 사실이 하나도 없으면 가중하지 않는다**(전부 `X`). 태도를 지어내지 않는다.

효과 — 기본점수가 모두 7.5인 CVE 3건:

| CVE | SIL3 안전 PLC (L1) | DMZ 히스토리안 (L3.5) |
|---|---|---|
| 가용성 `A:H` | **8.3** | 5.7 |
| 무결성 `I:H` | **8.3** | 7.5 |
| 기밀성 `C:H` | **0.0** | **9.3** |

기밀성 CVE가 PLC에서 0.0이 되는 것은 반박이 아니다 — 소유자가 "민감데이터 없음"을 선언해 `MC:N`이 적용된 결과이고, 상태는 `affected` 그대로다. 반박으로 인한 0.0과 구분하기 위해 `score.zero_reason` 이 `refuted` / `no_impact_lands` 로 표시된다.

| E (Exploit Code Maturity) | KEV 등재 → `E:H`(실제 악용 관측 = 정의 그대로). EPSS는 확률이지 성숙도가 아니므로 백분위 ≥0.95에서 **`E:P` 까지만** 허용 |
| RL (Remediation Level) | CSAF remediation 범주: `vendor_fix`→`O`, `mitigation`→`T`, `workaround`→`W`, `none_available`/`no_fix_planned`→`U` |
| RC (Report Confidence) | NVD 발표 벡터 + CISA 권고 근거 → `C` |

검증: NVD가 발표한 **CVSS 기본점수 10,980건을 오차 0으로 재현**했다
(`python src/cvss.py`, v3 10,205건 + v2 775건). 환경점수가 믿을 만하려면
기본점수 산술이 우리 해석이 아니어야 한다.

### 3.7 운영맥락 항목의 표준 근거 (traceability)

맥락 항목이 CVE를 해제하는 이상, 심사에서 가장 먼저 나오는 질문은 **"그 24개 항목은 어디서
왔는가"**다. "저희가 관련 있다고 판단했습니다"는 인증 맥락에서 답이 되지 않는다. 따라서
모든 항목을 ICS 운영자가 이미 평가받고 있는 요구사항군에 정박시키고, 근거 없는 항목이
들어오면 자가진단이 깨지게 했다 (`src/context_standards.py`).

```bash
python src/context_standards.py     # 추적성 매트릭스 + 누락 + 검증상태
python src/ics_context.py           # 끝줄에 traceability OK/BROKEN
```

#### 일부러 수집하지 않는 요구사항군 — 이게 매핑보다 중요하다

맥락 양식이 일반 보안 설문지로 번지지 않게 하는 경계선이다. **VEX는 "악용이 발동될 수 있는가"를
묻고, 아래 요구사항군은 그 답을 바꾸지 않는다.**

| 제외 | 이유 |
|---|---|
| IEC 62443-3-3 **FR6** (Timely Response to Events) | 탐지·대응은 취약 코드의 도달성과 발동 가능성을 바꾸지 않는다. **IDS가 버퍼 오버플로를 도달 불가로 만들지 않는다.** |
| KR **보안위협 탐지** | FR6과 동일 — 악용을 *관측*할 뿐 전제조건을 제거하지 않는다 |
| KR **복구대응** | 악용 성공 *이후*에 작동하므로 결과(consequence)의 문제이지 악용 가능성의 문제가 아니다 |
| KR **교육훈련** | 운영자가 속을 *확률*을 바꾼다. `UI:R`이 묻는 것은 "대화형 운영자가 **존재하는가**"라는 전제조건이고, 그가 얼마나 잘 훈련됐는지는 확률이라 아무것도 반박할 수 없다 |

이 네 건은 `context_standards.EXCLUDED` 에 사유와 함께 기록돼 있고, **사유 없이 빠진
요구사항군은 `coverage()` 가 `UNEXPLAINED` 로 보고한다** — 누락이 조용히 발생하지 않게 하기
위해서다(매핑 오류는 지적이라도 받지만, 누락은 아무도 질문하지 않는다).


## 4. 측정 — 이 방법론이 실제로 얼마를 판정하는가

코퍼스의 운영맥락 보유율이 0%이므로(W9) 실제 자산 맥락이 없다. 한 자산의 속성을
꾸며내 "방법의 정확도"로 보고하는 것은, 제거된 구형 `AV × exposure` 합성추정과
같은 오류다. 정직하게 측정 가능한 것은 **민감도**다: 현실적인 자산 원형이 주어졌을 때
실제 식별 CVE 모집단의 얼마를 결정하는가.

`python tools/eval_context_vex.py` — 모집단 **11,550 CVE**(벡터 보유 10,980 = 95.1%)

| 자산 원형 | affected | not_affected | under_inv | env≥9.0 |
|---|---|---|---|---|
| L1 헤드리스 PLC, 격리 셀 | 5,129 | **5,851** | 570 | 139 |
| SIS 로직솔버, 포트 포팅 + 하드웨어 다이오드 | 328 | **10,652** | 570 | 9 |
| L2 HMI / 엔지니어링 워크스테이션 | 10,980 | **0** | 570 | 198 |
| L3.5 DMZ 히스토리안, 벤더 원격접속 | 10,980 | **0** | 570 | 1,701 |
| 무선가능 RTU, 라디오 미장착 | 8,691 | **2,289** | 570 | 221 |
| **맥락 미제공 (대조군)** | 10,980 | **0** | 570 | 1,318 |

읽는 법:

- **대조군이 0건 해제한다.** 맥락을 안 넣으면 아무것도 면제되지 않는다 — 빈 양식이
  분석처럼 보이지 않게 하는 의도된 실패 모드다(`readiness()` 가 이를 보고한다).
- **L2 HMI도 0건 해제한다.** 사람이 쓰고, 계정이 있고, 로컬 실행이 되고, 포트가 열린
  자산에는 맥락이 줄 수 있는 면제가 없다. 맥락 추론이 만능이 아니라는 증거다.
- 해제는 **헤드리스·봉인 자산에 집중**된다. 그리고 그 전부가 소유자의 구조적 주장
  한두 개에 걸려 있다(L1의 5,851건 중 3,542건이 "로컬 실행 불가" 하나에서 나온다).
  그래서 W14의 UNATTESTED 경고가 장식이 아니다.
- **CR/IR/AR 를 켜도 어느 자산의 상태도 바뀌지 않았고 우선순위만 움직였다** — 점수와 상태가 제대로 분리돼 있다는 대조 확인이다. L1 PLC `env≥9`: 1→139, DMZ 히스토리안 1,318→1,701인데 평균은 7.08→6.96으로 **내려갔다** — 정보 자산에서 기밀성 중심 CVE가 9점을 넘어서는 동안 가용성 중심 CVE가 가라앉았기 때문이다. 대조군은 1,318에서 전혀 움직이지 않았다 — 임무 사실을 하나도 선언하지 않았으므로 가중될 근거가 없다.
- `under_investigation` 570건은 CVSS 벡터가 없는 CVE 수와 정확히 일치한다(W11).
  분석을 하고 반박을 못 찾은 것이 아니라, **분석을 시작할 수 없는** 경우다.

## 5. 한계 — 이 방법론이 틀릴 수 있는 지점

1. **구조적 사실은 사람의 주장이다.** "라디오 모듈 미장착", "포트 포팅됨"을 이
   파이프라인은 검증하지 않는다. 검증에는 물리 점검이 필요하고 그것은 소프트웨어
   파이프라인 밖이다. 따라서 의존성을 문서에 드러내는 것이 정직한 처리다
   (`evidence_basis`, `attested_by`, UNATTESTED 경고).
2. **반박은 점수화된 경로에 한정된다** (§3.5).
3. **CVSS 벡터 자체가 제품 일반에 대한 평가다.** 특정 주문 변종이 다르게 구성될 수
   있고, PR 반박은 그 가정에 가장 민감하다.
4. **CVSS v4가 없다.** 코퍼스에서 v4 벡터는 7건뿐이다. v4의 Safety(SA)·Automatable
   보조 메트릭은 ICS에 가장 적합한데도 쓸 수 없고, 그 역할을 자산 측 임무 사실
   (SIL, 안전기능, 가용성 허용도)이 CR/IR/AR 로 대신한다.
5. **소스 arm은 2.3%다.** 267건의 코드 수준 결과는 유효하지만 전체의 대표 표본이
   아니며, 그 숫자를 전체 성능으로 인용하면 안 된다.
