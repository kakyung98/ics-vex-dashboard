#3 evaluation SBOM 추출 자료

출처: prep/dataset.sqlite3, cases.fold = evaluation
총 18,608건 = 정상 대조군 9,304건 + 노이즈/누락 적용본 9,304건
원래 사례 ID를 보존했으며, 내용이 같은 SBOM도 합치지 않았습니다.
prep 폴더의 기존 12,418건 전수 점검 자료와 다른 평가셋입니다.

파일 구성
- sboms/<ID>.json: 모델 입력용 SBOM만 저장
- annotations/<ID>.json: 같은 ID의 정답, 원본 조건, 역할, 노이즈 기록
- gold.jsonl: annotations 전체를 한 줄에 한 건씩 모은 파일
- summary.json: 개수, 시나리오/역할/노이즈 규칙별 집계 및 검증 결과

정답 필드
- expected_cves: DB 원본 조건의 정답 CVE 목록
- unknown_cves: 미확정 CVE 목록. 음성 정답으로 해석하지 않습니다.
- gold: DB conditions.gold 전체를 그대로 보존
- source_condition: 원본 CPE, 버전 경계, 정규 필드, 버전 근거

노이즈 필드
- axis: control=정상 대조군, P2=제품명, P3=버전, P4=CPE
- scenario: control 또는 component/version/CPE의 noise/mask
- noise_applied: 노이즈 또는 누락 적용 여부
- perturbation.operator: 적용한 규칙
- perturbation.before / after: 변경 전 / 후 값
- control_sbom_id: 동일 원본 조건의 정상 대조군 SBOM ID
정상 대조군의 perturbation은 null입니다. null과 NOASSERTION 값을 그대로 보존합니다.

정답과 노이즈 정보는 모델 입력 SBOM과 별도로 저장했습니다.
이 자료는 출처 기반 합성 평가 자료이며 실제 운영 자산에 대한 독립 검증 정답은 아닙니다.

1. 먼저 구분해야 하는 숫자: CVE 수, 조건 수, SBOM 사례 수

이 폴더의 18,608은 CVE 개수가 아니라 평가용 SBOM 사례 개수입니다.
CVE 하나가 여러 제품·버전 조건과 연결될 수 있고, 같은 조건이 여러
CVE에 반복해서 등장할 수도 있으므로 CVE 수와 SBOM 수는 같지 않습니다.

전체 출발 모집단: CISA ICS 권고문 참조 CVE 12,418개
그중 이 CPE 기반 데이터셋의 대상: NVD CPE 기록이 있는 CVE 10,847개
나머지 1,571개는 이 노이즈 데이터셋에 포함되지 않습니다.
상위 폴더의 기존 12,418건 전수 점검 자료와 혼동하면 안 됩니다.

2. CVE에서 CPE 조건을 모으는 과정

대상 CVE들의 원본 NVD configuration 경로에 등장하는 CPE match 기록은
총 145,204개입니다. 이는 취약 제품 기록과 플랫폼/비취약 기록을 포함한
원본 출현 횟수이며, CVE 개수나 생성할 SBOM 개수가 아닙니다.

이 기록의 고유 CPE 문자열(criteria)은 40,660개입니다.
실제 생성 기준은 CPE 문자열만이 아니라 다음 다섯 값의 조합입니다.
  - criteria: 원본 CPE 문자열
  - versionStartIncluding: 시작 버전 이상
  - versionStartExcluding: 시작 버전 초과
  - versionEndIncluding: 끝 버전 이하
  - versionEndExcluding: 끝 버전 미만
버전 경계가 없으면 미지정 값을 그대로 유지합니다.

같은 조합이 여러 CVE에서 반복되면 조건 하나로 묶고 원본 연결을 보존합니다.
같은 CPE라도 버전 경계가 다르면 다른 조건입니다. 예를 들어 CPE 문자열은
같아도 '3.0 미만'과 '4.0 미만'은 별도 조건입니다.
그 결과 전체 고유 CPE·버전 범위 조건은 50,860개가 됩니다.
이 숫자는 서로 다른 제품 50,860종을 뜻하지 않습니다.

3. 왜 평가 조건이 9,304개인가

보존된 CVE_split.json의 CVE 분할은 다음과 같습니다.
  - train:       7,593개 CVE
  - evaluation:  3,254개 CVE
  - 합계:       10,847개 CVE

기존 문서에서 말하는 7:3은 이 CVE 분할 기준입니다.
현재 DB에 저장된 조건의 실제 fold 집계는 다음과 같습니다.
  - train 조건:      41,556개
  - evaluation 조건:  9,304개
  - 전체 조건:       50,860개

따라서 9,304는 '3,254 CVE × 일정한 개수'로 만든 숫자도 아니고,
'50,860 조건 × 30%'를 반올림한 숫자도 아닙니다.
CVE마다 연결된 조건 수가 다르고, 공유 조건도 있기 때문에 CVE 분할 비율과
조건/SBOM 분할 비율은 달라집니다. 이 추출에서는 분할을 다시 계산하거나
변경하지 않고 DB conditions.fold 및 cases.fold의 evaluation을 사용했습니다.

원본 source_coverage에는 플랫폼 등 역할을 포함한 연결이 들어 있습니다.
그 연결에 CVE ID가 나타난다는 사실만으로 해당 CVE가 양성 정답이 되지는
않습니다. 양성 정답은 gold.expected_cves로 확인해야 합니다.
실제 evaluation 조건의 expected_cves 합집합은 2,806개 CVE이며 모두
평가 CVE 분할에 속합니다. 평가 분할 CVE 3,254개 전체가 반드시 양성
정답을 갖는다는 뜻은 아닙니다. 미확정 상태는 그대로 보존합니다.

4. 왜 조건당 대조군 1개 + 변형본 1개인가

각 조건은 구성요소 하나를 담은 합성 SBOM의 기준이 됩니다.
동일 조건에서 다음 두 사례를 한 쌍으로 구성합니다.
  A. control: 실험용 노이즈를 추가하지 않은 기준 SBOM 1개
  B. fault: 제품명·버전·CPE 중 한 필드 계열에만 누락 또는 표기 변형을
     적용한 SBOM 1개

같은 원본 조건을 공유하는 기준본과 변형본을 비교하면, 추가한 입력 오류가
정규화 및 CVE 식별에 미치는 영향을 비교할 수 있습니다.
다른 제품이나 실제로 다른 버전을 넣어 정답을 바꾸는 설계가 아닙니다.
정답은 동일 원본 조건의 gold를 보존하고, 적용한 변경은 perturbation에
별도로 기록합니다. 이 설명은 실험 구성의 취지이며 성능 검증 결과가 아닙니다.

DB를 condition_id별로 집계한 결과 evaluation의 모든 조건 9,304개가
정확히 control 1개와 비control 1개를 갖습니다. 두 사례의 fold도 같습니다.

  9,304개 평가 조건 × (기준본 1개 + 변형본 1개)
  = 기준본 9,304개 + 변형본 9,304개
  = 총 18,608개 평가 SBOM 사례

전체 데이터에도 같은 계산을 적용하면 다음과 같습니다.
  train:      41,556 × 2 =  83,112개
  evaluation:  9,304 × 2 =  18,608개
  전체:       50,860 × 2 = 101,720개

'정상 대조군'은 실험용 오류를 추가하지 않았다는 의미입니다.
모든 필드가 알려져 있거나, 실제 설비에서 수집되었거나, 해당 제품이
안전하다는 의미는 아닙니다. 원본의 미확정 정보가 남을 수 있습니다.

5. 변형본 9,304개의 역할별·시나리오별 구성

역할 / 대상 필드       누락(mask)    표기 변형(noise)    합계
P2 / 제품명              1,551             1,551        3,102
P3 / 버전                1,551             1,550        3,101
P4 / CPE                 1,551             1,550        3,101
합계                     4,653             4,651        9,304

9,304를 세 역할로 균등하게 나누면 3,101개씩이고 1개가 남습니다.
이 데이터의 배정 결과는 그 1개가 P2에 더해진 3,102 / 3,101 / 3,101입니다.
역할별 3,101개는 홀수이므로 누락과 표기 변형이 각각 1,551 / 1,550개입니다.
이 균등 배정은 실험 구성이지 현장 오류 발생 비율의 추정값이 아닙니다.

조건 하나마다 P2, P3, P4 오류를 모두 만든 것은 아닙니다.
조건마다 세 역할 중 한 역할의 변형본 하나만 만듭니다.
따라서 '9,304 × (대조군 1 + 세 역할 변형본 3)'으로 계산하지 않습니다.
control은 특정 역할만의 오류 사례가 아니라 해당 조건의 공통 기준본입니다.

표기 변형의 범위:
  - P2: 대소문자, 공백/밑줄, 앞뒤 공백, 인접 영문 글자 순서 오타
  - P3: 같은 버전 앞에 v, Version 또는 version 표기 추가
  - P4: CPE 접두부의 대소문자, 글자 순서, 공백 변형
누락은 DB에 저장된 null 또는 NOASSERTION 표현을 그대로 보존했습니다.
개별 파일의 정확한 변경은 annotations의 perturbation.operator,
perturbation.before, perturbation.after에서 확인할 수 있습니다.

sboms에는 사례 ID 기준 18,608개 파일이 있습니다.

원본 조건이나 사례가 다르면, 보이는 제품·버전 내용이 같더라도 원래 ID를

18,608은 의미상 내용 중복을 제거한 수가 아니라 원래 평가 사례 수입니다.
조건별 버전 범위·출처·대조군/변형본 관계를 보존하기 위해 합치지 않았습니다.

엑셀 필드 정의에 따른 형식 수정 (2026-11-19)
============================================================
현재 sboms는 원본 DB에서 추출한 제품·버전·CPE 값과 노이즈를 유지하면서
엑셀의 필드명 및 CycloneDX 1.7 JSON 구조에 맞춰 수정한 버전입니다.

엑셀 형식 수정 당시 원본 DB는 변경하지 않았습니다. 이후 역할 명칭 변경은 아래 절을 참고하십시오.

주요 변경: properties를 name/value 배열로 변환, SBOM_CREATION_DATE 및
SBOM_MODIFY_DATE로 명칭 정리, lifecycles=[{phase: operations}]로 변환,
bom_type을 properties로 이동, 문서 version=2 및 수정 시각 기록.
원래 생성 시각과 serialNumber는 유지했습니다.

주소·연락처·공급사·라이선스·바이너리 해시·purl은 원본에 없는 값을
추정하여 채우지 않았습니다. 빈 객체/배열/문자열 또는 생략으로 표시했습니다.
실제 바이너리 해시 대신 JSON 해시를 component.hashes에 넣지 않았습니다.

정답 및 perturbation은 그대로이며 annotations와 gold.jsonl에만 있습니다.
annotations.export_format.sbom_file_sha256은 현재 SBOM 파일의 SHA-256입니다.
source_input_sha256/source_semantic_sha256은 원본 DB 기준 해시로 유지합니다.

18,608개 모두 공식 CycloneDX 1.7 JSON Schema 검증을 통과했습니다.
이는 모든 의미 규칙까지 만족한다는 뜻은 아닙니다. 프로젝트 입력 계약이
사용하는 대표 자산/구성요소의 동일 bom-ref 연결을 보존했습니다.
CPE 노이즈 사례의 잘못된 접두부와 CPE 누락도 평가 목적에 따라 유지했습니다.
공식 JSON Schema 통과를 CPE 자체의 유효성이나 평가 정확도로 해석하지 마십시오.
형식 검증 수량과 결과 요약은 summary.json에 남아 있습니다.
