# #4 자산 운영 정보 입력 계약

이 문서는 운영자가 확인한 자료를 자동 판정기에 전달하는 방법이다. 빈 값과 `unknown`은 비영향의 근거가 아니다. 필드는 자산 유형별 공통 양식과 해당 CVE의 원문 조건별 질문으로 나뉜다. 자산 유형에 속한다는 이유만으로 기능의 존재나 활성 여부를 채우지 않는다.

필드의 가이드 위치와 프로젝트 해석 범위는 [가이드 근거 매핑](ITEM4_GUIDANCE_MAPPING.md)에 기록했다.

## 자산 유형별 추가 조사 항목

MITRE ATT&CK ICS 20.1의 자산 ID와 이름을 사용한다. 아래 조사 항목은 프로젝트가 정의한 입력이며 MITRE가 정한 VEX 질문 목록이 아니다. 모든 유형에 운영모드·인터페이스별 서비스·방향성 접근 규칙·정비 경로·파일 반입·인증·물리/로컬 접근을 공통으로 묻는다.

| ID | 자산 유형 | 추가 조사 항목 |
| --- | --- | --- |
| A0001 | Workstation | 프로젝트 파일 열기, 엔지니어링 연결, 이동식 매체 |
| A0002 | HMI | 프로젝트 반입, 원격 화면, 브라우저 콘텐츠 |
| A0003 | PLC | 프로그램 다운로드, RUN/PROGRAM 모드, 웹 관리 |
| A0004 | RTU | 명령 전달, 광역망 링크, 로컬 설정 |
| A0005 | IED | 보호 설정, 엔지니어링 프로토콜, 로컬 설정 |
| A0006 | Data Historian | 데이터 수집, DB 인터페이스, 업무망 복제 |
| A0007 | Control Server | 제어 프로토콜, HMI 연결, 서비스 계정 |
| A0008 | Application Server | 애플리케이션 엔드포인트, 플러그인, 서비스 계정 |
| A0009 | Data Gateway | 프로토콜 변환, 상하위 인터페이스, 쓰기 전달 |
| A0010 | Safety Controller | 안전 로직 다운로드, 정비 모드, 프로그래밍 접근 |
| A0011 | VPN Server | VPN 리스너, 터널 라우트, 클라이언트 역할 |
| A0012 | Jump Host | 원격 세션, 파일 리디렉션, 하위 자산 접근 |
| A0013 | Field I/O | 필드버스, 원격 설정, 펌웨어 갱신 |
| A0014 | Routers | 라우팅, 관리 인터페이스, ACL |
| A0015 | Switch | VLAN/포트, 관리 인터페이스, L3 라우팅 |
| A0016 | Firewall | 방화벽 규칙, 검사 모듈, VPN 기능 |
| A0017 | DCS Controller | 제어기 프로그래밍, 피어 연결, 정비 모드 |
| A0018 | PAC | 프로그램 다운로드, 모션/비전 기능, 외부 모듈 |

복합 역할은 `/api/item4/asset-schema`에 여러 ID를 전달해 합집합으로 받는다. 이 공통 양식의 답변은 CVE별 조건에 자동 복사하지 않는다. 재사용하려면 `common_facts.field_ids`와 근거의 `field_ids`로 실제 대응하는 질문을 명시한다.

상세 조사 양식은 `tools/item4_asset_form.py --asset-types A0002 A0003 --output form.json`으로 생성한다. `definition`에 질문과 JSON Schema가 있고 `input.values`에 조사 결과를 입력한다. 포트 범위, 접근 규칙·서비스·파일 경로·설정·역할 등 자료별 구조와 근거 ID를 검증한다. `--input form.json`으로 같은 양식을 검사한다. 이 양식은 현황 수집용이며 실제 자산/설정/시점 범위와 근거는 VEX 평가 케이스에 별도로 연결해야 한다.

`state=unknown`은 자료 미확인이고 `data=null`이다. 조사된 값은 `recorded`와 근거 ID를 사용한다. 조사 범위가 비어 있음을 확인한 경우에는 `recorded_empty`, 빈 배열, 근거 ID, 조사 범위를 나타내는 `coverage_scope`가 필요하다. 확인된 빈 목록도 CVE의 필수조건 불성립으로 자동 변환하지 않는다.

## CVE별 조건 질문

`GET /api/item4/cves/{cve}` 또는 CLI `inspect`에서 원문 인용, 조건 ID, 제품 참조, 조건별 필드와 요구 자료 유형을 확인한다. `case-template`은 모두 미확인인 입력 골격을 만든다.

각 조건의 `evidence.segment_id`로 `/api/item4/evidence?segment_id=...`를 조회하면 권고문 ID·문서 해시·원래 JSON Pointer·텍스트 해시·CVE/제품 범위를 확인할 수 있다. 조건에 저장된 `start`, `end`, `quote`는 해당 원문 텍스트 구간 기준이다. 해시는 인용의 출처를 추적하기 위한 것이며 인용 의미의 독립 정확도 점수가 아니다.

| 조건 | 필요한 운영 자료 | 주의점 |
| --- | --- | --- |
| 네트워크 접근 | 적용 ACL/방화벽 규칙, 라우팅, VPN/정비 경로 | 원문 인터페이스와 출발지 범위를 명시 |
| 기능 활성·설정 | 적용된 설정 출력, 해당 제품의 설정 의미 | 비활성 권고와 실제 비활성 상태를 구분 |
| 운영모드 | 현재 모드, 모드 전환·정비 기록 | 정상 운전 결과를 정비 모드에 재사용하지 않음 |
| 외부 입력 처리·사용자 행위 | 파일 반입 절차, 처리 프로그램 설정, 적용 통제 | 과거 미관측만으로 앞으로의 불가능을 판단하지 않음 |
| 물리·로컬·정비 접근 | 인터페이스 목록, 콘솔 통제, 정비 경로/예외 | 연결이 목록에 없다는 사실만으로 차단 확정 불가 |
| 정상 사용자의 로그인·권한 | 대상 인터페이스의 세션·역할 기록 | 공격자의 계정 보유와 구분 |
| 공격자의 인증·권한·입력 지배 | 외부 사실 확인 필요 | 운영자 계정 목록으로 자동 확정하지 않음 |
| 기타 조건 | 조건에 맞는 추가 자료 필요 | 자동 관측 매핑이 없으면 미확인 |

답변 `true`는 원문 조건 성립, `false`는 불성립, `unknown`은 확인되지 않음을 뜻한다. AND/OR를 합친 문장을 하나의 원자적 필드로 사용하지 않는다. 원문에 근거를 둔 개별 조건과 관계로 표현할 수 없으면 보류한다.

## 공통 범위와 자료

평가에는 `asset_id`, 원문 카탈로그의 `product_id`, 정확한 `build`, `config_baseline`, `mode`, 시간대가 있는 `evaluated_at`이 필요하다. 각 자료에 다음을 기록한다.

| 키 | 의미 |
| --- | --- |
| `id`, `kind` | 고유 자료 ID, 필드가 요구하는 자료 유형 |
| `source`, `quote` | 설정/기록의 출처와 실제 관련 내용 |
| `scope` | 위 자산·제품·빌드·설정·모드의 동일한 범위 |
| `observed_at`, `valid_until` | 관측 시각과 인정 유효기간 |
| `field_id` 또는 `field_ids` | 실제로 뒷받침하는 조건 질문 |
| `target`, `origin` | 관련 인터페이스/기능과 출발지/행위 주체 |
| `absence_assurance` | 불성립 근거일 때 `enforced` 또는 `complete_scope` |

설치 식별 자료는 `kind=asset_inventory`이고 `observed_product_id`, `observed_build`가 평가 범위와 정확히 같아야 한다. 빌드 `1.0`을 기록 `11.0`의 부분 문자열로 매칭하지 않는다. 사용자가 입력한 대응 관계와 자료의 진실성을 독립 측정으로 주장하지 않는다. 자료가 충돌하거나 만료되면 비영향으로 확정하지 않는다.

확장 API의 `/api/item4/products?q=제품명`, `/api/item4/product?product_id=원문제품ID`에서 원래 제품명·계층·원문 문서 참조를 확인한다. 버전 표현은 원문 그대로 보존한다. 검색은 조회 편의를 위한 문자열 검색이며 설치 제품 일치 판정이나 버전 범위 추론이 아니다. 운영자가 실제 인벤토리를 확인해 정확한 제품 참조와 빌드를 연결해야 한다. 임의로 제품 ID를 만들거나 비슷한 이름을 자동 확정하지 않는다.

`absence_assurance=enforced`는 실제 적용 통제가 그 조건을 막는다는 자료가 있을 때 사용한다. `complete_scope`는 관련 범위를 모두 조사한 자료가 있을 때 사용한다. 이 문자열만 입력한다고 통제 효과가 독립적으로 검증되는 것은 아니다. 정책 문서나 최근 이벤트 부재는 이 부정 근거를 대신하지 못한다.

## 토폴로지 입력

`topology.nodes`는 노드 ID 목록이고 `links`는 `id`, `source`, `target`, `service`, `state`, `evidence_ids`를 가진 방향성 링크다. `state`는 `allowed`, `blocked`, `unknown`이다. 링크 자료에는 해당 `link_id`와 `service`를 연결한다. 유효한 차단 자료가 없는 링크는 미확인으로 다룬다.

`queries`에는 CVE의 `field_id`, `origin`, `target`, `service`를 넣는다. `binding_evidence_ids`의 자료는 `kind=network_condition_binding`, 같은 필드·조건 ID, 원문 인용의 UTF-8 SHA-256인 `source_quote_sha256`, 같은 출발지·대상·서비스를 명시해야 한다. 이 연결이 없으면 다른 장비의 차단으로 원문 조건을 부정하지 않는다.

선이 없는 것을 차단으로 판단하려면 질의의 `connectivity_complete`, `origins_complete`, `maintenance_paths_complete`가 모두 참이어야 한다. `coverage_evidence_ids`로 지정한 `kind=network_inventory_complete` 자료에도 같은 세 표시와 노드 목록·출발지·대상·서비스가 있어야 한다. 예외 정비 경로나 알려지지 않은 링크가 있으면 미확인이다. 다른 프로토콜을 거치는 대화형 침해 연쇄는 단순 서비스 라우팅으로 합성하지 않는다.

관련 출발지는 인터넷만을 뜻하지 않는다. 원문이 출발지를 제한하지 않았다면 내부 엔지니어링 단말·허용된 정비 장비 등 가능한 출발지를 함께 조사해야 한다. 입력의 출발지 노드가 집합을 나타낸다면 그 구성원과 조사 범위도 근거에 명시해야 한다. 인터넷 차단 기록만으로 일반적인 ‘공격자가 서비스에 도달 가능’ 조건을 거짓으로 답하지 않는다.

## 가상의 판단 예시

아래는 논리를 설명하는 가상 원문이며 실제 CVE의 근거가 아니다.

- 원문이 “해당 취약점은 레거시 웹 기능이 활성화된 경우에만 악용 가능”으로 경로를 제한하고, 적용 설정과 제품 문서가 해당 기능의 비활성과 그 효과를 뒷받침하면 그 조건을 부정할 수 있다. 전체 적용 경로가 이 조건을 필요로 한다는 자동 검증도 통과해야 한다. ‘기능을 끄는 것을 권장’이라는 완화 문장만으로 같은 필수조건을 만들지는 않는다.
- 원문이 경로를 특정 외부 구간의 WAN 관리 인터페이스로 명시적으로 제한하고, 모든 관련 출발지·VPN·정비 예외를 조사한 적용 규칙이 이 인터페이스 접근을 차단하면 그 경로를 부정할 수 있다. 원문이 단순히 ‘원격 공격 가능’이라고만 했는데 인터넷 방화벽만 차단한 경우에는 내부 출발지까지 불가능하다고 확정할 수 없다.
- 원문이 웹 접근 **또는** 로컬 콘솔 접근이라는 두 대안을 제시하면 웹 경로 차단만으로 비영향이 되지 않는다. 로컬 경로가 미확인이면 전체 OR 결과도 미확인이다. 두 조건을 하나의 ‘물리 또는 로컬 접근’ 질문으로 합쳐 한쪽 차단을 전체 부정으로 사용하지 않는다.

## 결과 사용

전체 원문 경로가 명시적으로 제한되고, 필요한 모든 검증이 통과하고, 유효한 운영 자료가 각 경로를 하나 이상 반박할 때만 배포 범위의 `not_affected`가 가능하다. 그래프가 비거나 일부 경로만 차단되면 이 규칙을 통과하지 못한다.

판정에는 입력·원문 그래프·필드 해시와 조건/경로 값, 사용/거절 자료, 토폴로지 연결 검사를 기록한다. OpenVEX 대상 ID는 평가 입력 해시에 묶고 `status_notes`에 평가 시점·유효기간·배포 범위를 남긴다. 설정·모드·빌드·경로 또는 근거가 달라지면 새 입력으로 재평가한다.
