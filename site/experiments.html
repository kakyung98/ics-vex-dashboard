Precision은 어떻게 계산했나

Precision = TP / (TP + FP)

양성으로 출력한 결과 중 정답인 비율입니다. 출력하지 않은 정답은 FN이며 Recall에 반영합니다. 출력 0개를 Precision 100%나 통과로 처리하지 않습니다.

#3 · 출력한 모든 CVE 매핑을 채점

정답은 제품·버전·에디션의 CPE 원자 매핑입니다. 하나의 SBOM이 여러 CVE에 매핑되므로 TP 수는 CVE 모집단 수보다 클 수 있습니다. 대상 CVE 하나만 확인하지 않고 모든 출력 매핑을 비교했습니다.

TPFP미확정 출력FNRecall
683,48856162,22799.6752%

일반 Precision: 683,488 / (683,488 + 56) = 99.9918%
보수적 하한: 683,488 / (683,488 + 56 + 16) = 99.9895%

주 지표는 보수적 하한입니다. 미확정 CVE 2,670개 전체를 FP로 더하는 것이 아니라, 실제로 출력된 미확정 매핑 16개를 FP로 계산했습니다. 학습 계열 입력을 포함한 전수 점검으로, 독립 시험 성능과 구분해야 합니다.

#4 · affected 출력을 양성으로 채점

합성 세계에서 실제 영향이 참이면 TP, 거짓이면 FP입니다. 원시 모델과 모델+검증 로직을 따로 계산했습니다. 검증 로직은 관측 누락·충돌·만료나 근거 부족이 있으면 보류합니다.

검증 후 시험 Recall은 30.4010%, 보류율은 92.5261%입니다. 높은 Precision을 높은 탐지 커버리지나 실제 설비 정확도로 해석하면 안 됩니다.

#3 · 정상본에 한 종류의 오류를 주입

CPE가 있는 10,847개 CVE의 원문 항목 145,204개를 제품·버전 범위 조건 50,860개로 정리했습니다. CPE의 제조사·제품·버전·유형을 SBOM 필드로 옮기고, 버전 근거가 없으면 NOASSERTION으로 남겼습니다. 원본 CPE는 metadata.component.cpe에 보관했습니다.

각 조건에 정상본 1개와 오류본 1개를 만들어 101,720개의 원천 SBOM을 구성했습니다. 오류는 이름 누락·오탈자, 버전 누락·표기 변형, CPE 누락·접두부 표기 변형 중 한 종류입니다. 다른 제품·버전으로 교체하지 않고 같은 자산의 표기를 변형했습니다. 예: controller → ocntroller, 3.1.4 → v3.1.4, cpe: → CPE:.

한 필드만 변형했으므로 버전 필드를 지워도 CPE 안의 버전이 남을 수 있습니다. 남은 증거로 식별하는 시험입니다. 이번 H200 전수 평가는 이 오류 세트 전체와 별도로 CVE당 대표 정상 control 입력을 고정 선택했습니다.

대상 CVE와 선택 SBOM의 관계개수
매핑 양성8,439
매핑 음성1,309
CPE는 있으나 버전 범위 소속 미확정1,099
정확한 CPE 정답 근거 없음1,571

판정 가능 9,748개 = 양성 8,439 + 음성 1,309입니다. 미확정 2,670개 = 1,099 + 1,571입니다. 음성 1,309개는 선택 CPE가 vulnerable:false인 경우였습니다. 모든 CVE에 취약 제품의 양성 예제를 확보한 구성은 아닙니다. 전체 NVD 플랫폼 AND/OR 구성과 실제 환경 영향은 평가 범위에 포함하지 않았습니다.

#4 · 실제 CVE 조건에서 가상의 운영 상태 생성

조건부 세계를 구성할 수 있는 2,452개 CVE마다 조건 참·거짓, 핵심 관측 누락 두 종류, 관측 충돌, 만료의 여섯 상태를 만들었습니다. 별도 Boolean 시뮬레이터로 정답을 계산했습니다. 원문 조건이 부족한 9,966개 CVE는 보류 사례 하나씩 유지했습니다.

2,452 × 6 + 9,966 = 24,678개 사례

입력과 라벨은 별도 파일입니다. 라벨을 모델 입력으로 보내지 않았습니다. 정답 생성기와 예측기는 별도 코드이지만 원문·조건 초안을 공유합니다. 원문 의미의 독립 검토와 실제 설비 영향 검증은 미완료입니다.
