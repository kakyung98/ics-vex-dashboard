Three-axis VEX · Method and synthetic experiment ← Operational VEX

Asset type × CVE × operating information

Deterministic rule and proof evaluation. No LLM interprets answers or supplies a VEX verdict. This is an expert-review candidate. Source meaning, evidence truth, and reviewer identity have not been independently authenticated.

How the three axes participate

  1. Asset type: one of the original 18 categories, used to select and bind the actual operating profile. A type association never proves a vulnerability or non-applicability.
  2. CVE: exact CVE/product/source snapshot, source quotation and prerequisite AND/OR paths. Hash/span validation detects changed data; it does not validate source semantics. A human reviews candidate prerequisite meaning.
  3. Operating information: 54 source rows / 167 coded observations, registered exact inventory values, and reviewed asset/build/baseline/mode/origin evidence. No answer is inferred from prose.

Rules producing the four VEX states

ResultRequired evidence
affectedExact product/running-build identity plus a CVE-specific supplier or qualified product finding. A reachable path or a general control answer alone does not establish affected.
fixedProduct identity, a CVE-specific fix finding, and evidence that the fixed build is actually running. A planned patch does not suffice.
not_affectedProduct identity and a CVE-specific supplier/qualified no-impact finding; alternatively, reviewed exhaustive source paths structurally refuted by qualified analysis. Firewall blocking alone does not suffice.
under_investigationMissing, mismatched, unreviewed, expired, conflicting, ambiguous, unsupported, or non-exhaustive evidence. No preferred proof is silently selected.

Condition proofs bind an exact source-quote hash and a constrained NIST field domain. Known and unknown values use three-valued AND/OR/NOT. Blocking a registered path is reported separately from product VEX status. No cross-CVE, cross-build, or cross-origin answer reuse is implicit. Export repeats source and validity checks.

Selectable input and review

All 167 answer domains and English NIST evidence · Inventory/evidence schema · Coded proof schema

Choose operational findings, register actual evidence, link a CVE/product, and create a coded proof using the dropdowns. Review its original records and select its review checkbox. Imported proofs start unreviewed. Source, identity and time metadata are retained for audit. The engine evaluates codes and explicit links; a human remains responsible for accurately encoding what the original source demonstrates.

Frozen synthetic scenario benchmark

1,278 fictional cases · 18 asset types · 15 scenario families · one fictional CVE with a network prerequisite · no cases excluded · no training data. This is a controlled logic benchmark, not independent CVE-level classification validation. The input and ground-truth files were sealed before evaluation. Labels follow a separately declared scenario narrative table, not evaluator outputs. Repeated templates are correlated, and the scenario mix is not a field-prevalence estimate.

Affected precision95.24%

Affected recall66.67%

Abstention rate49.30%

Four-status exact accuracy49.30%

Precision = TP / (TP + FP) = 360 / (360 + 18) = 95.24%. The predeclared 90% precision target was met on this synthetic mixture. FN = 180; TN = 720; evaluation errors = 0. Every false positive is retained.

The 18 false positives are deliberately semantically false but structurally valid supplier attestations: one for each asset type. The engine cannot establish the truth of an authenticated-looking claim from its code or hash. This experiment does not demonstrate 95% accuracy on real ICS assets, real CVE extraction, or independent expert judgements. The nominal Wilson interval is in the JSON report, with an explicit warning that repeated scenario templates violate independent-sample assumptions.

Full CVE catalogue retention

All 12,418 fixed-population CVE records were integrity-checked and retained. 5,039 have source-path candidates; 7,379 have none. No missing prerequisites are invented. These are coverage and integrity counts, not independent classification accuracy. The 223,524 possible CVE/type pairs are a logical coverage count; this report does not claim to have measured real operating facts for those pairs.
