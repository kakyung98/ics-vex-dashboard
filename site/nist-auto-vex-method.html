← Operational VEX

BOM CVE → required operating facts → automatic VEX

The previous manual-proof workflow is superseded. Users do not select affected/fixed/not_affected or condition true/false. The server maps observed operating enums to predicates, evaluates the source expression, and generates VEX without an LLM. This implementation currently has 8 executable real-CVE vendor rules; other CVEs remain under investigation. Independent expert and real-deployment accuracy validation is outstanding.

Actual BOM workflow

  1. Select a component–CVE row from the identified BOM. The component's product and version are retained; prior BOM VEX conclusions are ignored.
  2. Select the actual asset type and bind the deployed component scope and source evidence. Asset type never supplies operating facts or a verdict.
  3. The selected CVE opens only its source-relevant questions. The 54-row / 167-detail NIST catalogue is optional reference material, not a mandatory questionnaire.
  4. Choose observed deployment, actual running version and relevant parameter values, original evidence and survey coverage. All unknown defaults remain unknown. No verdict or condition-truth selection exists.
  5. The server validates exact scope, observation times, evidence kinds, source/rule hashes and finite answer codes; maps each enum to the source predicate; evaluates AND/OR/NOT; combines version applicability and operating expression; saves the trace and exports OpenVEX.

Automatic status rules

ResultComputed condition
affectedDeployed product instance, observed running version in the affected range, and source-defined operating formula true.
fixedObserved running version reaches a manufacturer-specific fix threshold. A planned patch or a vendor fix notice without runtime evidence does not suffice. Unneeded configuration questions are hidden once a fixed running-version choice is made.
not_affectedComplete inventory proves the component absent; or the vendor explicitly lists the release branch as unaffected; or complete scoped records falsify an exhaustive vendor-defined affected configuration. The impact statement is limited to this instance/configuration and validity period.
under_investigationNo executable rule, unsupported/backported/prerelease version, uncertain product/library binding, missing facts, incomplete negative survey, conflicting records, expired evidence or unresolved identity. The engine never guesses safety from a missing rule.

A BOM appliance firmware version cannot stand in for its embedded OpenSSL library version. Manufacturer-specific comparators distinguish OpenSSL letter releases and PAN-OS maintenance-specific hotfixes; marketplace image labels and unrecognised vendor backports stay unknown. Firewall presence, backup, budgets and telemetry prose are not parsed into CVE predicates. All original evidence remains auditable; record truth and reviewer identity are not independently authenticated.

New experiment: the automatic operating-answer engine

878 frozen synthetic operating cases across 8 real CVEs. Input payloads contain operational enum values and evidence references, never product-status claims, proof conclusions, condition true/false assertions or the expected VEX label. Reference release tables and physical configurations are stored separately and were fixed before evaluation. The production evaluator is not used to label cases. This is a controlled source-rule benchmark, not an independent expert study.

Affected precision92.78%
Affected recall54.55%
Abstention38.72%
4-state accuracy on resolved references73.96%

Precision = 90 / (90 + 7) = 92.78%. FN = 75; predicted affected = 97; unexpected evaluation errors = 0. All 878 cases are retained. The predeclared 90% precision target was met for this synthetic mixture.

The fixture audit found 7 deliberately wrong operating facts and 1 unchanged negative control among the 8 corruption-variant cases. All 7 wrong facts produced false-positive affected decisions; they were not removed. The other 870 scenario variants had no false-positive affected decision. This demonstrates that a deterministic engine still depends on accurate inventory/configuration inputs. These rates depend on the declared scenario mix and are not estimates of real-world error rates.

160 backported/prerelease/otherwise unsupported release-reference cases are retained. Their actual affected status is not claimed to be known. Precision uses all predicted affected cases as its denominator, and any positive without a resolved reference would count conservatively as unverified/false positive; observed unverified positives = 0. Recall uses resolved actual affected cases. Four-state exact accuracy uses resolved references. Repeated observation variants share physical scenarios and are not independent field samples.
