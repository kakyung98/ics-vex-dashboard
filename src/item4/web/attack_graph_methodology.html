Vulnerability Exploitation Prerequisite and operating records

A generative LLM extracts source-bound VEP prerequisites and AND/OR/NOT relations, including product keys, exact source quotations and unresolved information. The server checks structure, quotations and product binding before compiling the MulVAL graph. The NLI classifier and legacy overlay have been removed. The two generative roles use separate adapters on the shared base model once their training and evaluation are verified. A generative LLM may compare original scoped operating records with each positive operating atom. Every selected record must consistently establish the current applied state; missing, conflicting or invalid evidence stays unknown. Negative findings require complete scope. A machine-generated extraction does not certify complete semantic coverage, so a false partial graph cannot establish not_affected. Documented fixed running versions remain a separate supplier-version check.

Graph scope and evidence

The graph represents CVE exploit prerequisites for one component and the recorded origin. Asset types are context, not proof of a technique or CVE prerequisite. Network links, credentials, lateral movement and cross-asset attack chains are not invented from asset types or ATT&CK technique ordering. Modeling those routes requires source-supported transitions and actual topology and access observations.

MulVAL generation and justification

The default generator is MulVAL/XSB. The source condition compiler emits explicit signed Datalog rules; MulVAL produces the vertices, arcs and derivation trace. Every imported inference is checked against its submitted premises and conclusion. The graph is generated before operating answers. Both polarities in its structural input are placeholders, not claims that the asset has both states. At assessment, each primitive receives true, false or unknown from validated operating records; NOT requires explicit opposite evidence and never follows from a missing fact.

Each inference retains the CVE source quotation, rule identifier and clause, observed records and hashes, scope, value and unresolved inputs. The assessment and exports bind the graph and generation receipt hashes. A source-prerequisite goal is not proof of code execution, service failure or a completed exploit. The generic remote-exploit rules are not used to manufacture a result from a CVE identifier alone. Missing MulVAL execution produces an unavailable graph and no path-dependent verdict; no Python-generated substitute is used.

The default source extractor is the generative LLM VEP contract. Earlier regex and NLI-reviewed extraction artifacts are historical research paths and are not fallback sources for current decisions. Automatic quote and rule checks are distinct from independent human semantic validation.

The generative operating-record reviewer produces predicate observations, the separate Exploitability Analysis Agent evaluates the graph and mitigation, and the VEX Generation stage exports the resulting canonical decision as OpenVEX or CycloneDX VEX. Explicit historical or unapplied excerpts are withheld by conservative lexical guards; this does not establish general temporal-language accuracy. All selected operating records must establish the same current state; unresolved records cannot be overridden by another record.

Source hashes and answer scope are rechecked on every assessment and export. A control is not accepted solely because it exists: its observed effect must block every route. This is an implementation of project decision rules, not independent proof of exploit success or real-asset accuracy.
